## 2. 导航冗余判断（问题 4）：「已装插件」该不该独立

### 2.1 两个页面各干什么
- 软件商店 `store.js`：索引 / 场景预设 / 分类 / 搜索 / 安装 / 停用 / 卸载，卡片有「已安装」徽标（`store.js:267-275`），顶部有「N 个已安装，M 个可升级 + 一键全部升级」（`store.js:343-351`）。
- 已装插件 `app.js:992 renderPluginsPanel`：7 列表格（插件/版本/最新版本/深度/运行方式/状态/操作）+ 升级汇总 + 每个插件的 iframe UI（`app.js:1390`）。

### 2.2 判断：**重复的是「列表」，不重复的是「插件 UI 宿主」**

| 能力 | 商店有 | 已装插件有 | 结论 |
|---|---|---|---|
| 列出已装 | ✅ 徽标 + 汇总 | ✅ 表格 | **重复** |
| 升级单个 | ✅ 卡片内 | ✅ 表格内 | **重复** |
| 停用 / 卸载 | ✅ | ❌ | 商店独占 |
| 运行状态 / 版本 / 深度 | 部分 | ✅ 完整 | 已装独占 |
| **插件自己的界面** | ❌ | ✅ iframe 沙箱 | **已装独占，不可删** |

**给判断**：**「已装插件」不该作为一级菜单独立存在，但也不能直接删——要拆成两半。**

1. **列表能力并进商店**：商店加 `[全部 | 已安装 | 可更新]` 三档 tab（宝塔 / 1Panel 通行做法），已安装/可升级从一级导航消失，导航减 1 项、减一次「该去哪个页看」的选择成本。当前 `store.js:833` 只有分类 chip（全部/运维/数据…），**没有装态 tab**，这是重复感的根因：用户装了插件后要在两个页面各看一遍同一批插件。
2. **插件 UI 从「已装插件」页挪成「插件」分区内的详情入口**：`app.js:1390` 的「插件 UI（独立沙箱）」现在把所有插件 iframe **平铺在同一页**，装 8 个插件就是一屏 8 个 iframe——这既是资源问题也是一屏塞满的问题。应改为「商店卡片 → 打开/管理」进单插件详情，状态表格作为详情页里的「运行信息」小节。

**理由一句话**：重复的不是入口，是「已装列表」这份数据被渲染了两遍；而真正独占的插件 UI 不该用一个一级菜单来承载。

## 4. 共性归纳（问题 3）

### 4.1 所有页面都有的问题（3 条，按影响排序）

1. **手机端不是「适配了」，是「大部分页面没写适配」**：`@media` 计数——`sites 0 / files 0 / store 0 / ssl 0 / firewall 0 / process 0 / tasks 0`。这 7 个页面完全依赖 `style.css` 的通用规则，而它们的核心内容都是宽表格（文件表 5 列、SSL 表、防火墙规则表、任务表 6 列）。**裁决 41 的「触摸目标 ≥44px」在页面级样式里也没有落实**（只有 `monitor.js:97`、`tasks` 的排序按钮这类零散写法）。
2. **「错误给人话」已经做到，但「错误给动作」只做到一半**：`container.js:153` 的 `'怎么办：' + action` 是全仓最好的范式（`discover`、`integrity`、`sites` 也走同款），而 `process.js:106`、`ssl.js:455`、`firewall` 的预览失败仍是 `原文拼接`。**同一个产品两套错误范式**，不是能力不够，是没统一。
3. **默认值/预设只在「连接类」页面成立**：`db` / `redis` / `tasks` / `sites` / `integrity` / `runtimes` 有真预设；`backup`（路径）、`ssl`（域名/部署）、`firewall`（端口）、`container`（创建）、`logs`（保留策略）**五个页面的默认值是「空」或「手动」**。用户的 5 条具体抱怨（备份/SSL/日志/容器/数据库）里 4 条落在这条上。

### 4.2 单页独有问题（不可泛化）

| 页面 | 独有问题 |
|---|---|
| SSL | 证书与站点无绑定关系，ACME 是「调外部客户端 + 人工确认」，没有一条从域名到生效的闭环 |
| 容器 | 没有创建/编排/exec，只有列表与启停 |
| 日志 | 切割是手动按钮，默认不切割、不留策略 |
| 进程 | 空态零引导、失败态零动作 |
| 数据库 | 「实例」术语 20+ 处（四原则明令禁用） |
| 备份 | 路径输入框没有自动发现（选了站点目录还要手打路径） |

### 4.3 导航结构本身的问题（3 条）

1. **24 项偏多，且「更多」抽屉里 19 项 = 用户要记「在哪一组」**：宝塔一级 10 项左右、1Panel 12 项左右。本产品把「存储/网络/安全/平台」四类全塞进同一个抽屉，抽屉里再分 4 组——分组没减少认知负担，只减少了首屏占用。
2. **语义重复 1 组**：软件商店 / 已装插件（§2）。
3. **同域能力分散**：排查类动作被切成「终端 / 进程 / 监控 / 日志」四项在运维组，「服务发现」却在平台组；「设置」在平台组末尾——用户找设置不会去平台组找。

### 4.4 只改 3 件事，收益最大

1. **合并商店与已装插件为「插件」一项（商店内加 `[全部 | 已安装 | 可更新]` tab，插件 UI 进详情）**——导航减 1 项、消灭一处重复列表、顺手把「一屏 8 个 iframe」拆掉。收益：用户第 12 条反馈直接闭环。
2. **统一「错误三件套 + 空态按钮」到所有页面**，以 `container.js:153` 的 `怎么办：<action>` 为唯一范式，回填 `process/ssl/firewall/audit` 等缺口。收益：一次改动覆盖全部页面，是「小白能看懂」这条原则的杠杆点。
3. **五个「默认值为空」的页面补上自动发现/预设**：备份路径按站点自动列、SSL 从站点一键签发、日志给「按天/按大小」默认策略、防火墙给常用端口芯片、容器补创建向导。收益：直接对应 5 条用户原话，且都是「不填也能成功」。

> 手机端适配不在「只改 3 件」里，但它是**唯一一个跨全部 7 个页面、且不修就一直被判定违反裁决 41** 的横向欠账，应作为独立轨道并行（见 §5 P1）。

## 7. 一句话结论

「简陋」不是 20 个互不相干的毛病，是 **3 个系统性缺口**：①默认值为空（5 个页面）②错误/空态范式没统一（1 个最差样本 `process.js:121`，1 个最佳样本 `container.js:153`）③7 个宽表格页面没做手机端适配。用户点名的 13 条里，**数据库/监控/日志切割/文件/计划任务/完整性/服务发现** 已经达到「合格」或「勉强可用」，真正该重做的是 **SSL、容器、备份路径、商店-插件合并** 这 4 处。
