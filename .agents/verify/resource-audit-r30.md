## 1. 结论：采用选项②「已到合理下限，不建议再投入」

task-249 对 5 类低风险候选逐条核实的结果：**候选 1（embed 冗余）、3（build flags）、4（重量级依赖）、5（首屏预算余量）全部无压缩空间**；唯一理论收益点「gzip 预压缩 embed」为**中风险、需实测且 idle 驻留收益不确定**，不构成派优化卡的理由。继续向 8 MiB 目标压，必须违反 G-01 薄壳红线（把能力移出内核）或 G-22（单纯调参）或 ADR-0023 单二进制零侵入（把 embed 改为外置静态目录）——这些都是设计层取舍，不是"低风险压缩"。

**处置：不派优化卡，转趋势看护。**

- 每个里程碑跑一次 `make mem MEM_POINTS=60`（约 65s，60 点中位数）记录 VmRSS / RssAnon / RssFile，作为趋势序列留档；日常 `make mem`（5 点）可作即时观测，但里程碑证据必须写明用了哪档（RESOURCE-MODEL.md §2.1、§7）。
- 判定沿用 ADR-0016 两层口径：**红线内（≤16,384 KiB）不返工**；介于目标 8,192 KiB 与红线之间记 WARN + 趋势，不触发阻断；差异 <10% 视为噪声，不重测、不追因。
- 不把 WARN 当失败，也不把"目标未达"包装成"已达标"——两条都如实记录。

| 构成 | KiB | 占 VmRSS | 属性 |
| --- | ---: | ---: | --- |

## 3. 口径更正：91,092 B 是首屏**用量**，不是余量

- 当前 `make frontend` 实测：首屏 gzip **91,092 B（用量）**，预算 307,200 B，**余量 = 307,200 − 91,092 = 216,108 B（约 70.4% 未用；精确 216108/307200 = 70.35%）**，仍在 ≤300 KiB 硬红线内，`make frontend` / G-03 首屏段 **exit 0**。历史快照 59,709 B（v1-budget-measure.md:37）与 81,528 B（perf-frontend.md:80）是旧值，以当前 91,092 B 为准。
- 91,092 B 同时触发 `scripts/frontend-check.sh` 的**体积漂移 WARN**：判据为 `> 基线+5%（87,341 B）或绝对线 90,000 B`（`:76-78`），当前因**绝对线**命中。**这是非阻断告警，不是 G-03 红线、不改退出码**（脚本明示 `[WARN]` 只打印、不改退出码），不得读成"预算告急"或"首屏超标"。
- **正确处置只有两条**（脚本 `:86-87` 原文口径）：① 增长属已评审的首屏必需功能 → 同轮签字更新脚本 `BASE_FILES` 基线快照并写来源；② 属"本该懒加载却被塞进首屏"的视图模块 → 拆回 `/assets/<视图>.js` 懒加载后复核。**不是压体积**——红线内压体积既无门禁收益，又可能牺牲功能或违背 UI 设计。
- 本条已同步进 `docs/RESOURCE-MODEL.md` §8 的首屏口径注记，防止后续把"用量"误读为"余量"或把 WARN 误判为 gate。

## 4. 竞品对照的诚实边界

- round 27 一手证据确认：**1Panel 官方 94 MB 是后台全栈占用，不是 RSS**；**宝塔（BT）没有一手数字**。两边都**没有与我方同口径的 RSS 数字**。
- 我方 RSS 优化的价值是**自身低消耗**（空载 14,228 KiB、红线内、无常驻后台开销），**不能作为"超越竞品"的证据**。
- **禁止把 14 MiB 与 94 MB 放进同一张表比较**：口径不同（RSS vs 后台全栈）、单位与形态不同，同表即误导。本卡不联网、不据二手数字下结论。

## 5. G-22 与进度纪律

- G-22：资源/性能改动必须先答"能否少一个进程 / 少一个依赖 / 改生命周期 / 改触发方式"；只有设计层与架构层穷尽才允许纯代码层调参，且调参必须记 ADR + 标注临时性。本轮正是**穷尽后认定无低风险空间**，因此不派卡、不调 `GOGC`/`GOMAXPROCS`/`GOMEMLIMIT`（现为默认档 `GOGC=50` / `GOMEMLIMIT=6MiB` / `GOMAXPROCS=min(NumCPU,8)`，ADR-0015 钉死）。
- 用户口径：**不为压缩停进度**。趋势看护只加一条里程碑采样动作（不阻断发版、不返工），不新增优化卡、不改行为。
