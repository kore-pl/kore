## 3. 认证 / 鉴权开销

| 序列 | n | min(ms) | p50(ms) | p95(ms) | p99(ms) | max(ms) | mean(ms) | HTTP 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `POST /api/v1/auth/login`（拿 token，5 次） | n=5 | 75.9086 | 76.0591 | 77.804 | 77.804 | 77.804 | 76.4088 | 200 |
| 未带会话拒绝路径 `GET /api/v1/system/info`（50 次，401） | n=50 | 0.1269 | 0.3219 | 0.5038 | 0.7585 | 0.7585 | 0.3461 | 401 |

- **login ≈ 76.4088ms**（5 次 75.9–77.8ms）：由 PBKDF2-SHA256 **600,000 次迭代**（`internal/core/auth/password.go:32` `HashIterations`，按 docs/SECURITY §3.3）主导，且经单飞串行化（`handlers_auth.go:110-119`），属**预期安全成本**，不是缺陷；每会话仅一次，之后操作免密。
- **带会话访问受保护端点的额外开销**：同端点 `system/info` 未鉴权 401 路径 p50=0.4516ms / p95=0.5665ms，带会话成功 200 路径 p50=0.507ms / p95=0.6228ms，增量约 **+0.0554ms(p50) / +0.0563ms(p95)**；此增量同时含会话校验（Validate/Touch/Slide，内存操作，`middleware.go:297-323`）与成功路径 handler 执行，量级为几十微秒，可忽略。
- **unauth 401 拒绝路径**：50 次全 401，p50=0.3219ms / p95=0.5038ms / max=0.7585ms——比成功路径更快（中间件短路，不进 handler），符合 fail-closed 且无拒绝放大。

## 4. 吞吐（单并发顺序 + 4/8/16 并发）

端点 `GET /-/healthz`，每档独立测 3 秒，错误 = 状态非 200：

| 并发 | 请求数 | 时长(s) | req/s | 错误数 | 错误率 |
| --- | --- | --- | --- | --- | --- |
| 1 | 7771 | 3.0 | 2590.1 | 0 | 0.0 |
| 4 | 11280 | 3.001 | 3759.0 | 0 | 0.0 |
| 8 | 10071 | 3.002 | 3354.3 | 0 | 0.0 |
| 16 | 7761 | 3.004 | 2583.3 | 0 | 0.0 |

读法与诚实边界：

- 客户端是**单进程 Python harness**（ThreadPoolExecutor 多线程受 GIL 约束）+ **每请求新建 TCP 连接**（connect/close 系统调用计入客户端开销）。吞吐曲线在 4 并发达峰（3759 req/s）、8/16 并发回落，是**客户端侧 GIL + 连接建立成为瓶颈**的典型形态，**不是服务端能力上限**。故以上 req/s 是「端到端观测值 / 服务端容量的保守下界」，不可解读为 kored 的极限吞吐。
- 零错误（4 档全 0）说明在观测压力下无崩溃、无拒绝、无状态异常；机器为 24 逻辑核、测试期间 loadavg≈3.9，未打满。

`POST /api/v1/alerts`（info/plugin 一条受控告警，**仅写入隔离实例 state**，无 webhook 配置故无出站）：单次 **4.8163ms**，HTTP 200（会话 cookie + X-Kore-CSRF 双提交通过）。写路径走 bbolt `Update`（fsync 落盘），毫秒级符合预期。未做任何会污染宿主数据的操作；该告警随隔离 state 目录在收尾时删除。

## 6. 归因与判据

**延迟花在哪（定性）**：

- 只读端点 healthz/system-info：路由（`ServeMux`）+ JSON 编码 + HTTP 写出 + 新连接建立，亚毫秒级；`system/info` 额外读启动期缓存的 envprobe 报告与内存 supervisor 统计（`handlers.go:165-180`），无文件/网络 I/O。
- 会话鉴权：内存 map 查找 + 5 分钟节流的 Touch + 滑动判定（`middleware.go:297-323`），增量几十微秒。
- 登录：PBKDF2 600k 迭代（`password.go:32/90`）主导 ~76ms，**设计如此**（口令派生防暴力破解），单飞串行避免并发放大猜测吞吐。
- 写告警：bbolt fsync 落盘主导 ~4.8ms。
- 吞吐：受客户端 GIL / 连接建立约束，非服务端瓶颈。

**性能红线**（`docs/V1-GOALS.md:45`、`docs/PLAN.md:244-245`、`docs/ROADMAP.md:142`：API p95 ≤50ms 本地 200 次、启动到就绪 ≤1s；lazy p95 ≤300ms 为 M2 起生效，本隔离实例无 lazy 插件、不在本卡范围）：

| 判据 | 红线 | 实测 | 结论 |
| --- | --- | --- | --- |
| API p95（本地 200 次） | ≤50ms | 最慢序列 `system/info authed` p95=0.6228ms；`healthz` p95=0.5748ms | **PASS**（余量约 60–87 倍） |
| 启动到就绪 | ≤1000ms | 152.29ms | **PASS** |
| 5xx / 拒绝放大 | 无 | 所有序列 5xx=0；401 路径更快 | **PASS** |

**结论：健康，无需优化。** 依据：①全部 API 序列 p95 ≤0.623ms、p99 ≤0.819ms，距 50ms 红线有两个数量级余量；②启动 152ms 远低于 1s；③零错误；④唯一「慢」点是 login ~76ms，但它是 PBKDF2 安全成本的必然结果、每会话仅一次、且单飞串行，非缺陷。本轮**未发现值得另派优化卡的真实瓶颈**。

## 7. 诚实边界与未验证项

- 单机单实例、无竞品同口径对照；结论只证明 kore 自身基线，**不构成性能超越竞品的证据**。
- 吞吐数字受客户端 Python GIL 约束，为保守观测值而非服务端极限；如需服务端容量上限，需在同机用原生并发工具（或多进程客户端 + keep-alive）另测。
- 端到端延迟含新建 TCP 连接（非 keep-alive），比浏览器实际体验偏高，属保守口径。
- 本轮只测进程对外 HTTP 面，未做 pprof / CPU profile（任务允许「定性即可」）；`perm-system-cost.md` 提的「审计 deny 路径 fsync 写放大 QPS」仍需单独微基准，不在本卡范围。
- 被测二进制为仓库自带 `bin/kored` 的逐字节副本（沙箱无法 go build，原因见 §1），非本轮从 HEAD 源码现场编译；HEAD 源码与该产物一致性由仓库构建纪律保证，未在本次测量中重新编译验证。
