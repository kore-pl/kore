## 2. lead 的理解与关键判断

1. **先把契约钉死，再写代码**：M0 只交付文档、骨架与门禁，零业务代码；路径、预算、协议字段、错误码先写进 `docs/`，M1 只照抄。
2. **薄壳是不可让渡的定位**：`internal/core` 多一行业务逻辑就是设计事故，"能不能少一个进程 / 少一个依赖"优先于"能不能调小一个参数"。
3. **插件必须能独立演进**：独立仓库、独立 tag、独立 CI；内核只对外暴露 `pkg/pluginapi`，这条决定了后续所有拓扑与版本线选择。
4. **资源预算是门禁不是口号**：同时常驻进程数是结构性问题，22 × 12 MiB 不是优化能填的坑，必须靠生命周期设计解决。
5. **证据优先于自述**：每个任务完成判据是"命令 + 退出码 + 关键输出"，写的人不给自己发合格证。

## 3. 本轮裁决

按 [DECISIONS](../DECISIONS.md) 的议题名引用（编号见该表行序）：

- 仓库拓扑（N+2）与 `pkg/pluginapi` 嵌套 module —— 解红队 F-10 死锁。
- 插件 IPC 线格式：UDS + 4B 大端长度 + JSON，**无额外帧头**（否决 2B 帧头、1B nibble、NDJSON）。
- 生命周期三态，`lazy` 为默认；常驻收敛为 `site` + `monitor`，`cron` 转 lazy 且由宿主调度器触发、主壳零定时器。
- 预设常驻目标 ≤ 19.2 MiB（24 MiB 的 80%），余量为 0 判 FAIL。
- v1 范围：22 能力域 = 12 生产级 + 8 基础级 + 6 不做；v1.0 Linux GA，Windows / macOS preview。
- 深度分级 canonical 名单逐插件点名，`echo` 为验证件不评级。
- 依赖白名单只约束第三方（≤3）；同仓嵌套 module 不计配额但必须 `replace => ./`，跨仓 `replace` 禁止提交。
- 安装两入口共用 `installer`；预设安装失败 = 整预设事务回滚，M2 不提供 `--allow-partial`。
- 新增 G-19 空闲行为 / G-20 深度等级 / G-21 无副作用诊断 / G-22 优化顺序。
- 验收分级：阻断级 vs 记录级，只剩记录级可提交；`verify/` 排除 docs-check 元信息、保留链接可达。
- 叙事口径统一：二进制 / 进程 = `kored`，项目 / module = `kore`，systemd unit = `kore.service`，Kore Loop = 七阶段。
