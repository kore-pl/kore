## 2. lead 的理解与关键判断

1. **M1 不新增业务范围**：只把 M0 的退出条件拆成可派任务，把三个不确定性（体积 / RSS、帧编解码 + 生命周期、跨仓 tag）写成命令级判据。
2. **协议先于插件**：先冻结 `pkg/pluginapi` 公开面 → 打 `pkg/pluginapi/v0.1.0` → `echo` 才能用 tag 依赖；否则 F-10 死锁会以 `replace` 假通过的形式复活。
3. **测量必须独立**：内存基线由 verifier 单独采样，不复用 implementer 的数字；这也直接暴露了 GC 被副作用关闭的 P0。
4. **判据必须语义化**：`grep` 只能当代理指标，否则实现者会为了"变绿"改写法而不是改顺序（M1-01 即判例）。
5. **不为几百 KiB 返工**：预算改两层后，M1–M3 只在 >16 MiB 时阻断，目标 8 MiB 进趋势，M4 集中瘦身。

## 3. 本轮裁决

- 预算三次调整后定案：**红线 16 / 24 / 48 MiB + 目标 8 / 12 / 24 MiB**，只有红线判 gate（ADR-0016）。
- 运行时锚点 `GOGC=50` + `GOMEMLIMIT=6MiB` + `GOMAXPROCS=8`，并明确它是**临时代码层手段**、非达标主因（ADR-0015）。
- 验收判据去正则化：M1-01 由 `grep 'make([]byte, n)'` 改为"读代码路径确认校验先于分配"，并写明不得据字面量判 FAIL。
- 协议边界语义：`timeout_ms<=0` → 15000；`id` 校验归 `bus`；`Event` 含 `seq`/`ts`；JSON 会话最小载荷 2 字节、protobuf 按连接编码放宽。
- 内存证据协议：三档 `GOGC` × 60 点中位数 + 记录 HEAD / sha256 + 生效值 + 来源标注；GC 判别只看 `/gc/gogc:percent`。
- GC 副作用 P0：禁止 `SetGCPercent(-1)` / `SetMemoryLimit(-1)` 式"设置即读取"，落成 G-21。
- 两个 replace 分治：同仓 `replace => ./` 必须提交，跨仓 `replace` 禁止提交、只放 `go.work`。
- hello 两层时限：2s 硬超时（exec→hello）与 300ms 冷启动 SLO 分开计，不合并成一个数。

## 5. 事故

### 5.1 GC 被诊断代码关闭（P0）

- **现象**：GOGC 三档消融无差异（6300 / 6372 / 6304 KiB，最大差 72 KiB），`gctrace` 全程仅 1 次 GC。
- **根因**：`cmd/kored/serve.go:82` 在日志调用里写 `debug.SetGCPercent(-1)`；Go 文档明确"负数禁用 GC"，"打印当前值"实际执行的是"关掉 GC"。
- **影响**：ADR-0015 的默认档从未生效，历史内存数字（6408 / 7200 / 7832 / 7820 / 8056 KiB）全部在 GC 关闭状态下采集。
- **修复**：改为记录"自己设置的值"或走 `runtime/metrics`；补回归测试（分配内存必须观察到 GC 增长）；落 G-21。
- **方法论纠正**：`NumGC` 不是可靠判别器——`GOMEMLIMIT` 生效时 GOGC=off 也会触发 GC（实测 churn 128 MiB 时 `numgc_delta=15`），唯一可靠指标是 `/gc/gogc:percent`。

### 5.2 测量被并发干扰

- 23:42 首轮档 A 结束后 `bin/` 被并发构建 / `make clean` 删除，B/C/D 档启动失败；改用冻结副本重测。
- 23:44–23:49 出现他人制造的 `comm=kored` 假进程（pid 51943，`prctl` 改名的 python），一度干扰进程计数；最终 `pgrep -x kored` 为空。
- 5s 稳定期不足：A2 窗口内 `RssFile` 从 3764 涨到 5108，改用 20s 稳定后与 A1 一致（6300）。

### 5.3 预算三次调整

初始 8 / 12 / 24 → 分层（红线 / 不阻断 / 观测）→ 定案 16 / 24 / 48 + 目标 8 / 12 / 24。驱动因素不是"放松要求"，而是实测暴露"守 8 MiB 必须同时压两个旋钮并已返工多轮"，而真正的膨胀风险（大依赖树、常驻进程暴涨）不需要靠几百 KiB 的拉锯来防。

## 6. 遗留

1. M1 运行期只支持 `resident`；`lazy` / `oneshot` 接受字段并返回 `E_UNSUPPORTED`（message 写明"M2 支持"），不算缺陷（G-14）。
2. 修复后基线 7,688 KiB 由 implementer 提供，**verifier 未独立复跑**；里程碑收口须用 `MEM_POINTS=60` 复测（`m1-memory-baseline.md` §9.3/§9.4）。
3. `internal/core/config` / `store` / `registry` 已在工作区落盘但未提交，对应任务仍 `in_progress`。
4. 8 MiB 目标未达成但在 16 MiB 红线内：按 ADR-0016 不得因此推迟发布，M4 集中瘦身。
5. 本轮新增的判断台账本身需要下一次里程碑复核：条目是否覆盖、owner 推断是否被补正。
