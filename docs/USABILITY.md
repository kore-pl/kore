# USABILITY — 易用性四原则（硬性设计约束）

## 0. 为什么有这份文档

2026-11-23 用户原话：「还有一点操作要方便，设计方面要多考虑预设和自定义，还有操作步骤尽量少，小白能够看懂和使用。」

现状是**给老手用的**：数据库页要配 `KORE_MYSQL_INSTANCES` 环境变量再重启、日志页要配 `KORE_LOGS_SOURCES`、SSL 页要粘贴 PEM 文本、备份页要手填路径与白名单——老手能忍，小白到第一步就放弃。商店与预设机制解决"装什么"，本文件解决"装上之后怎么让人用得动"。

**这是硬约束，不是建议**：四条原则的判据在评审与验收时逐条核对，不满足即返工。入口级红线见 [AGENTS.md](../AGENTS.md)「读前必知」第 7 条，前端落地约束见 [FRONTEND.md](./FRONTEND.md) §12，产品定位见 [VISION.md](./VISION.md)。

## 0.1 适用面

| 项 | 内容 |

| 读者 | architect（提案评审）、implementer（照此实现）、verifier（照此验收）、red-team（照此找"看着简单实际挖坑"） |

## 1. 原则 1：预设优先，自定义兜底

- 每个功能必须有「一键 / 默认」入口，参数已预填：端口、路径、字符集、备份目标用探测值或业界默认，不要求用户先想清楚再动手。
- 高级参数折叠在「自定义」里，默认不展开；展开后必须能一键回到预设值，不能只进不出。
- 落地要求：预设值集中在模板 / 常量里，一处维护；页面不得各自硬编码默认值，更不得用示例域名、示例路径占位。
- 常见违规：首屏直接铺一排空字段；「自定义」点开后没有回退；默认值写死 `example.com` / `/var/www/example`。
- **判据**：完成核心任务的点击次数 ≤ 3；不填任何高级参数也能成功。

## 2. 原则 2：自动发现，不让人填环境细节

- 本机有什么服务（nginx / mysql / redis / php / node）由系统探测，不要求用户填路径、端口、socket、版本。
- 探测不到时才让用户手填，且同时给出「怎么装」的指引（一条安装命令 + 装完怎么复检），不是丢一个空输入框。
- 探测结果必须可见可改：字段旁标注来源（自动检测 / 手工填写），用户改过的值不得被下一次探测覆盖。
- 落地要求：探测走统一入口（复用启动期探测，不各页面自写一套命令）；结果带来源与时间戳，并提供「重新检测」按钮。
- 常见违规：让用户填配置文件路径；探测失败只写"未检测到"；用户手填后每次刷新又被探测值改回去。
- **判据**：页面首次打开时，可自动填的字段已填好，并标注「已自动检测」。

## 3. 原则 3：操作步骤尽量少

- 一个任务一次表单、一次提交：参数在一次交互里收齐，不做"先建再配再启用"的三段式。
- 需要多步的（如建站 + SSL、建库 + 建用户 + 授权）用「向导」串起来：一条进度、一次确认，不做成三个页面各干一半。
- 每一步都要能回退到上一步且保留已填内容；失败重试不重填。
- 落地要求：多步流程用同一套向导壳（显示"第 N 步 / 共 M 步"），中间状态可恢复；跨页面只存"半截配置"的写法一律不认。
- 常见违规：建站要先去目录页建根目录、再到网站页填域名、最后去 SSL 页签证书，三处各存一半。
- **判据**：列出每个功能的任务步骤数，> 3 步的必须合并；合并不了的，必须证明"拆开是用户要求"而不是实现方便。

## 4. 原则 4：小白能看懂

- 所有错误提示给「怎么办」，不是错误码：说清哪一步失败、可能原因、现在点哪个按钮能修；错误码放 `title` 或折叠区。
- 所有配置项有中文标签 + 一行帮助说明；帮助说明写"填什么 / 不填会怎样 / 推荐值"，不写"参见文档"。
- 空状态必须给「下一步做什么」的按钮，不是空白页、不是"暂无数据"四个字。
- 不用「实例」「生命周期」「capability」「revision」这类内部术语，用「数据库连接」「运行方式」这类白话；术语必须出现在 [GLOSSARY.md](./GLOSSARY.md) 才算有定义。
- 落地要求：错误对象统一三件套——白话 `message` + 怎么办的 `hint` + 折叠的错误码；文案评审必须覆盖空态、错误态、成功态三种。
- 常见违规：提示 `E_PLUGIN_STATE_CONFLICT`；空状态只有"暂无数据"；帮助文案写"详见文档"；把 JSON 原样甩给用户。
- **判据**：随机抽 3 个页面，把文案给一个非技术用户看，能说出这页是干什么的。

### 4.1 术语对照（内部说法 → 用户看到的说法）

| 别用 | 用 |
| --- | --- |
| 实例 / instance | 数据库连接 |
| 生命周期 / lifecycle | 运行方式 |
| capability | 权限（能做什么） |
| revision | 版本 |
| preset | 预设方案 |
| supervisor | 进程管理 |

新增术语必须先落 [GLOSSARY.md](./GLOSSARY.md)，再进 UI；UI 里出现内部术语按原则 4 违规处理。

### 5.1 改造顺序（按违反条数排，先建可复用模式）

1. **备份页**（违反 1、2、4 三条）：先做出「探测默认值 + 折叠高级项 + 白话错误」的完整样板。
2. **数据库页 / 日志页**（各 2、4 两条）：复用同一套「自动探测 + 已自动检测标注」，不再各自发明。
3. **SSL 页**（1、4 两条）：预设「一键自签」，PEM 粘贴降级到「导入已有证书」折叠区。
4. **网站页**（3 一条）：域名 + 站点根目录 + 建目录合成一次表单，一次提交。

理由：先把覆盖面最广的共用模式（探测 / 预设 / 白话文案）做出来，后面三页是复用而不是重写；反过来先改单点，等于把同样的轮子造四遍。

## 6. 评审与验收怎么用

- **设计评审四问**（新功能提案必答，答不出退回提案阶段）：默认入口是什么（原则 1）／哪些字段能自动探测（原则 2）／用户要点几次（原则 3）／文案给小白看得懂吗（原则 4）。
- **验收证据**（不接受"感觉挺顺手"）：点击次数数出来、探测字段截图、任务步骤数列表、3 页文案给非技术用户看的结果，一并写进验收报告。
- **抽样防作弊**：原则 4 的 3 个页面由 verifier 随机指定，实现者不得自己挑；抽样结果与原文回答一起归档，不许只写"通过了"。
- **与其它门禁的关系**：本文件只管"人能不能用"；资源预算见 [RESOURCE-MODEL.md](./RESOURCE-MODEL.md)，UI 双端截图证据见 [FRONTEND.md](./FRONTEND.md) §11（G-28），安全边界见 [SECURITY.md](./SECURITY.md)。简化的是操作，不是边界——易用性不得以突破预算、放宽鉴权为代价。

## 7. 边界：什么不算"更简单"

- 不为了少一步而砍掉必要确认：删除、覆盖、恢复仍需二次确认（危险操作的可逆性优先于点击次数）。
- 不为了少一个字段而猜错：探测失败就明确说"没检测到"，不许静默填一个看似合理的错值。
- 不为了"小白友好"隐藏能力：高级参数折叠不等于删除，老手的路必须留着。
- 不与 6 项不做清单冲突：不做拖拽建站、不做多语言、不做模板市场（见 [AGENTS.md](../AGENTS.md) G-11）。
