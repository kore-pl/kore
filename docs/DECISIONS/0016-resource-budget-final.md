# ADR-0016: 资源预算最终定案——硬红线与目标分离

## 背景

M1 期间用户两次调整口径：「没必要把限制卡得太死，优先设计」「8 MiB 也不是必须卡死」。原因不是放松要求，而是实测暴露了结构问题：空载 VmRSS 在 **7.7 MiB（GC 缺陷修复后）** 与 **8.5 MiB（24 线程档）** 之间波动，为守住 8 MiB 必须同时压 `GOGC=50` 与 `GOMAXPROCS=8` 两个旋钮，且已因此返工多轮。

更关键的是"卡死 8 MiB"是错的靶子：项目真正要对标的是**比同类面板低一个数量级**（同类常驻数百 MiB），不是某个具体 MiB 数。把 8 MiB 当红线，会让 M2 每加一个模块都触发一次预算返工，而真正的膨胀风险（例如引入一棵大依赖树）反而被"几百 KiB 的拉锯"掩盖。

## 决策

**硬红线（判未完成）与目标（争取，不判）分离**：

| 指标 | 硬红线（判未完成） | 目标（争取，不判） |
| --- | --- | --- |
| 主壳空载 VmRSS | ≤ 16 MiB | 8 MiB |
| 单常驻插件 | ≤ 24 MiB | 12 MiB |
| 常驻合计 | ≤ 48 MiB | 24 MiB |
| 同时常驻数 | ≤ 3（推荐 ≤2） | 1–2 |
| 单二进制 | ≤ 25 MiB | 15 MiB |
| 前端首屏 gzip | ≤ 300 KiB | — |
| 空闲 CPU | ≤ 0.1%（60s ≤ 60ms） | 0 |
| goroutine / fd / 出站 | ≤ 20 / ≤ 64 / 0 | — |

规则：**只有硬红线判 gate**；目标值只进趋势记录，不阻断里程碑。M4 收口时按红线判，目标值超标记 WARN 并在里程碑报告里说明。

## 备选方案对比

| 方案 | 优点 | 代价 | 为何不选 |
| --- | --- | --- | --- |
| 卡死 8 MiB | 承诺最硬，宣传最好听 | 逼出 GOGC / GOMAXPROCS 调参、多轮返工；M2 加模块必破 | 已证伪：返工成本高于收益 |
| 不设上限 | 完全自由，零返工 | 无法验证"不成负担"；同类面板的膨胀没有刹车 | 违背资源锚点 |
| 硬红线 16 MiB + 目标 8 MiB（选） | 设计自由度回来；门禁仍能拦住真正的膨胀；对外承诺仍低一个数量级 | 需要向用户解释"红线 / 目标"两层 | 选它：把"防膨胀"与"追求极致"分开 |
| 按宿主机内存比例动态 | 小机器更友好 | 行为不可预测，用户无法预判；门禁无法给固定阈值 | 运维工具最忌"同版本不同环境表现不同" |

## 后果

**正面**：M2/M3 不再为几百 KiB 返工，设计层有空间做正确的事；门禁仍能拦住"引入大依赖 / 常驻进程暴涨"这类真实膨胀（16 MiB 对薄壳仍是极严的线）；对外可讲"同类面板低一个数量级"，这是可验证的量级差，不是抠数字。

**负面**："16 MiB"不如"8 MiB"好宣传，README 必须同时写清红线与目标，否则会被读成"退步"；红线放宽后，若长期停在 15 MiB 附近，目标值会失去约束力。

**技术债**：M4 瘦身冲刺仍要做 pprof（目标是 8 MiB），但不再为几百 KiB 阻断里程碑；预算表成为唯一口径后，`AGENTS.md` G-03 与 [RESOURCE-MODEL](../RESOURCE-MODEL.md) 的表述需同步为"红线 / 目标"两层，否则三处数字会打架。

## 验证方式

```bash
make budget-check     # 判红线；目标值只出 WARN，不改退出码
make mem              # 记录趋势（日常 5 点 / 收口 MEM_POINTS=60）
make idle             # 空闲 CPU / threads / fd / 出站 / 定时器
```

里程碑报告里必须同时给"红线是否通过"与"目标值趋势"两项，不能只报一个数。

## 复审条件

**除非出现安全事故或用户明确要求，不再调整本表。** 调整必须新开 ADR，并说明"为何现有红线不足以拦住实际风险"；若 M4 收口时目标值 8 MiB 未达成但在红线内，**不得因此推迟发布**——按 [ADR-0014](./0014-v1-scope-and-depth-tiers.md) 的口径，v1.0 的 gate 是红线。
