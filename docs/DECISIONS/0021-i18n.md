# ADR-0021: 以中文为默认语言的轻量 i18n——零依赖字符串表，英文可选并回退中文

## 背景

产品定位是中文用户环境里的服务器面板：界面、错误提示、帮助文案、插件描述**天然是中文**，`web/index.html` 的 `lang` 也早已是 `zh-CN`。但此前文案是硬编码的，代价是：

- **无法给非中文用户用**：一个英文母语的运维看「概览 / 已装插件 / 防火墙」只能猜；`info.json` 的 `description` 也全是中文。
- **文案没有单一真源**：同一句「正在加载」「模块加载失败」在 `shell.js`、`app.js`、各视图模块里各写一遍，改口径要全仓 grep。
- **现状规模**：`web/*.js` 共 26 个模块、中文文案 1425 个字符（`app.js` 231 / `db.js` 151 / `store.js` 145 最多）；`internal/core` 非测试 Go 文件里中文 message 1234 行、分布在 91 个文件；插件 `info.json` 的 `description` 为中文。

因此要引入 i18n，但方向必须钉死：**中文是默认与一等公民，其他语言是附加**——不是"英文优先再翻译成中文"，也不做浏览器语言猜测。

**与既有非目标的关系**：`AGENTS.md` G-11 把「多语言（i18n）」列为 6 项不做。本条 ADR 把该非目标**收窄**为「不引入全量多语言框架/翻译生态」：中文仍是唯一完整语言，英文只覆盖导航 + 通用组件 + 设置页。G-11 与本条冲突时以本条为准，其余非目标不变。

## 备选方案对比

| 方案 | 对首屏预算的影响 | 迁移成本 | 中文主导性 | 后续扩展 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A. 前后端各自字符串表（`zh-CN` 默认）| 中（表随首屏加载）| 低（按页迁移）| 强（中文即默认表）| 加语言=加一个文件 | **采纳（零依赖变体）** |
| B. 只做中文，放弃 i18n | 零 | 零 | 强 | 永远只有中文 | 不采纳 |
| C. 完整 i18n 框架（i18next / vue-i18n 等）| 高（框架 + 运行时 + 插件生态）| 高（全量改 key）| 弱（默认语言可被框架配置改掉）| 强 | 不采纳 |

**B. 只做中文**
- 优点：零成本、零风险，与现有硬编码完全一致。
- 缺点：用户明确要求「中文为主、其他为辅」——"辅"也是需求；且硬编码分散的问题依旧存在（同一句文案多处重复）。**不采纳。**

**C. 引入第三方 i18n 框架**
- 优点：复数、日期、命名空间、懒加载一应俱全，社区成熟。
- 缺点：① 违反零第三方依赖与 300 KiB 首屏预算（`FRONTEND` §7、G-03），i18next + 插件通常 30–90 KiB gzip，是首屏余量的两位数百分比；② 我们的需求只有"两个语言、六十条文案、回退"，用不到复数/ICU；③ 框架会带来自己的加载时序与缓存策略，与"首屏同步、其余按需"的壳冲突。**不采纳。**

**A. 零依赖字符串表（采纳）**
- 前端：两份普通对象（`zh-CN` 全量、`en-US` 可缺项）+ 一个 ≈100 行的 `t(key, params)`；缺项回退中文表。
- 后端：`internal/core/i18n/zh-CN.go` 是主表，M5 再接 `Accept-Language`（本轮**只设计不实现**）。
- 代价：需要人工保证两份表的键一致（用回退兜底，不会显示键名）；没有复数/日期格式化——本项目文案没有复数需求，日期一律 ISO/本地化格式串手工拼。

## 关键决策

1. **默认语言固定 `zh-CN`，不做浏览器语言检测**。不读 `navigator.language`、不读 `Accept-Language` 猜首屏语言：猜错会让中文用户看到英文界面，违背"中文为主"。语言只由设置页显式选择。
2. **切换入口只有设置页**，两个选项（`中文（简体）` / `English`），够用即可；选择写入 `localStorage['kore_locale']`，下次启动直接生效。
3. **未翻译的 key 回退中文表，绝不回退成键名**。查找顺序：当前语言表 → `zh-CN` 表 → key（仅两表都缺时返回 key，作为开发期信号；壳层 `tr()` 再用硬编码中文兜底，正常交付不会露出键名）。
4. **后端错误消息中文为主**。错误对象继续「白话 message + hint + 折叠错误码」；`Accept-Language: en` 时返回英文**延到 M5**，本轮不改任何 `internal/core` 的 message——内核零改动，避免范围爆炸。
5. **运行时文件名拍平**。源码按 `web/i18n/<locale>.js` 组织，但内核静态路由只托管单段文件名（`server.go` 的 `handleAsset` 拒绝含 `/` 的路径），因此构建产物是 `web/dist/i18n-zh-CN.js` / `i18n-en-US.js`。**不为了子目录去放宽内核的遍历面**——一个 UI 便利不值得扩大静态托管的攻击面。
6. **首屏预算新增硬口径**：`i18n.js` + `i18n-zh-CN.js` 的 gzip 合计 ≤ **3 KiB**，由 `scripts/frontend-check.sh` 独立卡（不靠 300 KiB 总预算的余量）；`en-US.js` 只在切英文时注入，不进首屏。

## 文件组织

| 文件 | 角色 | 约束 |
| --- | --- | --- |
| `web/i18n/zh-CN.js` | 主语言，全量 | 新增文案先写这里；键名 `域.条目` |
| `web/i18n/en-US.js` | 辅助语言，可缺项 | 缺项回退中文；不得新增中文表里没有的键 |
| `web/i18n.js` | `t()` / `setLocale()` / `onChange()` | ≤120 行，零依赖，默认 `zh-CN` |
| `internal/core/i18n/zh-CN.go` | 后端消息主表（M5） | 本轮不落地，先在 ADR 定形 |

## 迁移策略：不做全量迁移

26 个视图模块全量改 key 是几百处改动、没有任何用户可见收益，**本轮只迁移三层**：

| 范围 | 内容 | 状态 |
| --- | --- | --- |
| 导航 | 18 项标签 + 4 个分组标题 + 「更多」抽屉 + 无障碍标签 | 本轮完成 |
| 通用组件 | 加载 / 空态 / 错误 / 按钮（`common.*`，约 20 键） | 键已备好，壳层先用 |
| 设置页 | 语言卡片（标题、说明、选项、失败提示） | 本轮完成 |
| 页面内部文案 | 各视图的表单标签、表格头、帮助文案 | **暂不迁移**，后续按页替换 |

覆盖度现状：中文表 52 键，`en-US` 52 键（导航 18 / 骨架 11 / 通用 16 / 设置 7）。

## 后果与复审条件

- **正面**：导航与设置页可整体切换语言；文案有单一真源；新增语言是"加一个文件"，不动内核与视图。
- **负面**：两种语言并存期间，英文界面会出现"导航英文、页面中文"的混合态——这是**明确的阶段性取舍**，由本 ADR 承认，不当作缺陷修。
- **复审条件**：① 引入第三门语言时，重新评估是否需要框架（复数/语序）；② 页面内部文案迁移超过 3 个页面时，补一份 key 命名规范；③ M5 落地后端 i18n 时，另起 ADR 定 `Accept-Language` 协商与回退链。
