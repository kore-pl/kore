# ADR-0025: 索引签名体系重设计（长期密钥 vs 每版换钥）

## 0. 判据（用户原话）

> 「第 40 把重签？？？这东西设计有问题吧」

质疑成立。不是"再签一次就好"，而是**签名仪式本身把三条成本绑成了死结**：换密钥 → 公钥进二进制 → 必须重启；同步靠手工 grep；私钥用完即 shred。本 ADR 只出草案，**不改代码/脚本**。

## 1. 现状代价链（39 把累计）

| 环节 | 现状 | 代码/文档证据 |
| --- | --- | --- |
| 每版生成新 ed25519 密钥 | 签完 `shred -u`，seed/priv/der 均不落盘 | `.agents/verify/resign-39.md` §2「私钥用后 shred」 |
| 公钥内置为编译期常量 | `const IndexPublicKeyHex` | `internal/core/market/verify.go:16` |
| 换钥 = 改常量 + 重新编译 | 换公钥必须 `make build` 并重启 kored | `docs/RELEASE.md:36`、`docs/RUNBOOK.md` §1 |
| 两端公钥逐字一致靠手工 grep | `validate-index.sh` 与 `verify.go` 两处常量 | `resign-39.md` §4 闸门：`grep -c <新公钥>` = 1、旧公钥 = 0 |
| 每次留仪式记录 | `resign-NN.md` + 私钥销毁证据 | `.agents/verify/resign-*.md` |

**39 次**的累计成本：39 次密钥生成/销毁、39 次公钥同步、39 次主实例重启（18:13 SIGTERM 事故正是这条链的衍生故障）。第 40 把已在排队。

**问题的本质**：把「信任根」与「密钥材料」绑成同一个编译期常量。常规体系（apt / npm / GPG）里，信任根是**发布者身份**，密钥材料可轮换；我们把两者等同，于是每次轮换都必须重建软件。

## 2. 三个独立问题

1. **密钥生命周期**：每版换钥不是安全要求，是"私钥零留存"的极端化。零留存防的是"私钥在磁盘上被窃"，但代价是公钥高频变化。
2. **信任根的位置**：公钥编译进二进制 → 任何密钥变化都变成软件发版 + 重启；这与"索引只是数据"的定位冲突。
3. **同步一致性**：两处常量靠人工 grep 保证，属"纪律型正确"，不是"机制型正确"。

## 3. 候选方案

### 候选 A：长期签名密钥（私钥 0600 受保护，公钥永不变）

**做法**：发布方持一个长期 ed25519 私钥（存 `<install>/data/keys/index-signing-<keyid>.seed`，0600、属主 root，`<install>` 内）；`IndexPublicKeyHex` 固定不变；索引重签只签正文，**不重建软件、不重启**。

- **安全影响**：私钥泄漏 → 攻击者可伪造索引（含 `download_url` / sha256）→ 可指向攻击者控制的 release。**缓解**：①私钥只在发布机、0600 + 磁盘加密；②`download_url` 限定 `https://github.com/kore-pl/*`（内核已校验），攻击者还需 GitHub 组织写权限才能托管恶意包；③sha256 与 release 资产双约束；④泄漏后按"轮换 ADR"走一次换钥（此时仍要 rebuild+restart，但属事故响应，不是日常）。
- **实施成本**：低（~0.5 人日）：sign-index.sh 改为读固定密钥文件；文档改"重签"流程；39→1 次重启。
- **G-29 运行态边界**：私钥在 `<install>/data/`（安装目录内），属运行态资产，不入 git；发布机操作不改主实例配置。
- **G-31 零侵入**：兼容——密钥在安装根内，不新增系统路径；`<install>/data` 已被 ADR-0023 覆盖。
- **否决点**：轮换仍需重启（仅从"每版"降到"泄漏/策略变更时"）。

### 候选 B：公钥外置 + 指纹内置（换钥免重启，指纹变才重建）

**做法**：二进制只内置**稳定的信任根标识**（如 `key-domain = kore-pl/index-v1` + 初始指纹）；运行时从 `<install>/data/keys/index-pub.json` 读当前公钥，并校验该文件由**上一把密钥签名的 key manifest**（轮换链）。换钥 = 发布新 key manifest（旧钥签名）+ 新公钥文件；**指纹/信任根不变 → 不重建、不重启**。若信任根标识本身要变（迁移组织/换代），才 rebuild。

- **安全影响**：与 A 同级，但多一层"轮换链"复杂度；manifest 签名链断了 → fail-closed（和现在验签失败一致）。外置公钥文件被替换无效（需旧钥签名），除非攻击者同时拿到旧钥（等价于 A 的泄漏面）。
- **实施成本**：中（~2–3 人日）：verify.go 改为"内置 domain + 读 manifest + 验链"；`validate-index.sh` 改为校验链；发布脚本加 key manifest 生成。
- **G-29**：公钥/manifest 在 `<install>/data/keys/`；读取为只读，运行期不写。
- **G-31**：兼容（安装根内）。
- **否决点**：比 A 复杂；在"只有单一发布者、无多签需求"的当前规模下，收益是"轮换也免重启"，而轮换本就低频。

### 候选 C：维持现状（每版 shred 换钥），仅批量攒批降频

**做法**：不改机制，把"每版重签"改成"每 N 版 / 每阶段重签一次"，减少次数。

- **安全影响**：与现状相同（零留存），但**攒批期间索引与实包不一致**的窗口变长（当前已出现"索引声明 sha ≠ HEAD 重打包"的漂移，见 Gitea #1 的同类风险），且 401 窗口变长。
- **实施成本**：极低（0 人日，只改纪律）。
- **G-29/G-31**：不变。
- **否决点**：治标不治本——重启链、手工 grep、仪式成本都还在；攒批还会放大索引漂移。

### 候选 D：B + 长期钥组合（目标态）

**做法**：**长期密钥（A）作为日常**（一份私钥、公钥常量稳定，重签不重启）；**B 作为轮换机制**（若需换钥，用旧钥签 key manifest 完成无重启轮换；只有信任根换代才 rebuild）。即：A 解决 99% 的日常，B 兜住低频轮换。

- **安全影响**：等同 A，且轮换路径明确（旧钥签 manifest，不引入 TOFU 窗口）。
- **实施成本**：分两期：一期 A（0.5 人日，立刻把 39 次重启降为 0）；二期 B（2–3 人日，按需）。
- **G-29/G-31**：同 A/B，全部落在 `<install>/data/keys/`。
- **推荐理由**：先摘掉最贵的"每版重启"，再补轮换机制；两期都可独立验收、独立回滚。

## 4. 对比与推荐

| 维度 | A 长期钥 | B 外置+指纹 | C 维持现状 | D = A+B |
| --- | --- | --- | --- | --- |
| 日常重签免重启 | ✅ | ✅ | ❌ | ✅ |
| 轮换免重启 | ❌（需 rebuild） | ✅ | — | ✅ |
| 私钥留存风险 | 中（0600 + 发布机） | 中 | 极低（零留存） | 中 |
| 实施成本 | 低 | 中 | 极低 | 低→中（分两期） |
| 索引/实包漂移窗口 | 不变 | 不变 | **变大** | 不变 |
| G-29 兼容 | ✅（`<install>/data`） | ✅ | ✅ | ✅ |
| G-31 兼容 | ✅ | ✅ | ✅ | ✅ |

**推荐：D（分期落地，先 A 后 B）**。

1. **一期 A（立即做）**：长期私钥 + 固定公钥常量；重签不再 rebuild/重启；把 39 次重启链一刀切断；`resign-NN.md` 改为"重签记录（不换钥）"，只在轮换时留仪式。
2. **二期 B（按需）**：密钥轮换走 key manifest（旧钥签名），只有信任根换代才 rebuild；`validate-index.sh` 校验链完整性。
3. **被否决**：C（治标，且放大索引漂移窗口）；纯 A 不够（轮换仍要重启，但可作为一期独立交付，不阻塞）。

**不推荐一步到位 B**：当前只有单一发布者、无多签/多人授权需求，直接上 manifest 链是过度设计；A 的 0.5 人日就能消灭主要痛点。

## 5. 实施边界（本轮不做）

- 本期只出草案：**不改** `verify.go`、`sign-index.sh`、`validate-index.sh`、`RELEASE.md`、`RUNBOOK.md`；
- 落地时必须先补：密钥生成与备份 SOP（含离线备份位置、恢复演练）、泄漏响应流程（吊销 + 换钥 + 重发）、`kore-plugins` 与 `kore` 两端常量的单一真源（例如由 `validate-index.sh` 从 verify.go 抽取比较，而不是人工 grep）；
- 密钥属"不可回滚资产"：生成/销毁前必须由用户确认（与私钥相关操作按既有纪律先问）。

## 6. 复审条件

1. 私钥泄漏或疑似泄漏 → 立即走轮换（A 的 rebuild + 重启，或 B 的 manifest）；
2. 引入第二个发布者 / 需要多签 → 重新评估 B 的 manifest 模型；
3. 索引格式或信任根换代（换组织、换算法）→ 单独 ADR；
4. 若 3 个月内重签次数 < 3，可降级为"仅 A"，不实施 B。

## 8. 实现记录（2026-11-23，方案 A 一期）

- **脚本**：`kore-plugins/scripts/sign-index.sh` 改为读长期私钥——优先 `$KORE_SIGNING_KEY`，缺省 `~/.config/kore/signing/index-signing.seed`；缺失时 **exit 2** 并指向 [SIGNING-KEY-SOP](../SIGNING-KEY-SOP.md)，不再静默生成新钥；`--generate` 仅首次播种（已存在则 exit 3，拒绝覆盖），打印公钥供两端常量固定；兼容旧 `KORE_INDEX_KEY`（已弃用，仅过渡）。
- **文档**：新增 [SIGNING-KEY-SOP](../SIGNING-KEY-SOP.md)（首次生成/备份/日常重签/轮换=二期 B/泄漏应急/复核周期）；[RELEASE](../RELEASE.md) 第 7–8 步改为“重签免 build 免重启”。
- **不动**：`verify.go` 与 `validate-index.sh` 的公钥常量本轮**未变**（仍 `8b4fe19f…`）；不重签真索引（第 41 把另派）。
- **自测**：临时密钥目录 + 副本索引：`--generate` 0、缺钥 2、重签 0、验签 0、篡改 1；两端公钥常量 before==after；真索引 `git status` 干净。
- **残余**：私钥轮换仍需一次 rebuild+restart（二期 B）；`KORE_INDEX_KEY` 旧路径保留一个周期后删除。

## 9. 追加修订记录：验签索引新增内核资产条目（2026-11-26；§0–§8 原文不动）

> 本节是 **append-only 修订记录**，不改上文已 accepted 正文（与 [ADR-0023 §11](./0023-zero-intrusion.md) 同口径）。触发来源：[ADR-0059 §3.2](./0059-silent-update-trigger-and-supply-chain.md)（供应链：已验签索引 → https 资产 → sha256）与 [自更新实现任务图](./self-update-implementation-plan.md) M6。登记本段即解除 M6 的 ADR 门槛，实现（索引字段显式化 + 下载链）按 M6 任务卡另行派发。**本段只定字段语义与验签规则，不改验签体系本身，也不代表索引文件已增条目。**

1. **新增条目类型**：在现有验签索引的条目体系里增加一类**内核资产条目**（与插件条目同属同一已签名索引，共用方案 A 的长期签名密钥与验签链）。它与插件条目的区别只在"下载后交给谁"：插件包交 `store/install`，内核资产交 `kored upgrade --bin`。信任根不变——只消费经 `market.Verify`（ADR-0025 方案 A 固定公钥常量）验过的索引，未验签索引不得作为下载来源。
2. **字段语义（G-24 显式类型，禁 `any` / `object` / `map[string]any`）**：内核资产条目对外结构体**逐字段显式列类型**——`download_url`（string，发布物地址）、`sha256`（string，64 位小写 hex 摘要）、`version`（string，目标内核版本）、`size_bytes`（int64，包字节数）以及内核资产专属标识字段；不得用 `any` / `object` / `map[string]any` 兜底，也不得用 `json.RawMessage` 承载这些字段（`json.RawMessage` 的受控例外只限插件方法参数/结果载荷，不适用内核资产条目）。内部解析若临时用 `any`，必须在一处收口并转成上述具体类型后才进入下载链。
3. **`download_url` 与 `sha256` 的验签规则**：
   - `download_url` 必须是 **https 绝对 URL**；省略、`file:` / `http:` 等非 https scheme 一律拒绝（复用安装器既有校验，`download_test.go:125` 反例），离线包走显式本地路径、不伪装成索引下载。**禁止 URL 拼接猜测**：缺 `download_url` 直接 `E_INVALID`、零下载（`download_test.go:109-118` 先例）。
   - `sha256` 必须存在且形态合法（64 位小写 hex），缺摘要的条目在加载期即被 `validateIndex` 拒掉。**校验先于替换**：下载流式计算摘要并与索引逐字比对，不一致则目标字节不动（`upgrade.go:12-13` 既有不变量）。
   - 内核二进制先下载到**本地临时文件**，再交 `kored upgrade --bin <本地文件> --sha256 <hex>`（该命令拒 URL，`upgrade.go:10-14`），复用原子替换 + `.prev` + pending + `--no-block` 重启 + 新进程 finalize 的完整链；market 只负责"从已验签索引取 URL 与摘要并触发"，不自建第二条下载/安装链路（G-01/G-13）。
4. **公钥轮换口径（沿用 §7，不变）**：验签公钥是编译期常量，**换公钥必须 rebuild + 重启才生效**（`docs/RUNBOOK.md` §1）；日常重签（方案 A，不换钥）仍免 rebuild / 免重启。轮换属事故响应 / 低频操作，不因本段新增内核资产条目而放宽——新二进制重启后自然承接新公钥，验签失败按 fail-closed 处理，绝不降级为"用未签名索引继续"。
5. **边界与复审**：本段不触发任何远端写操作（全流程零 git push / tag / PR / CI，ADR-0056 §6；GitHub 只 `workflow_dispatch`）；不新增安装目录外写入（G-31 / ADR-0023）；若未来出现第二种资产类型或需要改验签信任根（换组织 / 换算法），须另开 ADR，不得援引本段类推。
