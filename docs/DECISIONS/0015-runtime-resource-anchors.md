# ADR-0015: 运行时资源锚点——GOGC=50 + GOMAXPROCS=8 的实测依据

## 背景

M1-02 首次对 `bin/kored` 做真实空载实测。**下列数字是 M1 观测值（GC 修复前/后需重测），不作为 M4 收口依据**，待 `.agents/verify/m1-memory-baseline.md` 复核后才算可引用样本。采样口径：`make budget-check`，日常 5 点、收口 `MEM_POINTS=60`，起进程后先等 5s 稳定再开始采；拆分来源 `status`（RssAnon / RssFile）。

为什么收口口径是 60 点：**5 点在 GC 周期面前太短**——`GOGC=50` 下堆峰值可能几十秒才出现一次，5 点容易刚好避开峰值，得到"好看但不真实"的数；60 点覆盖至少一个完整 GC 周期，中位数才代表稳态。日常 5 点只用于看趋势，两者差异 < 10% 视为噪声，不重测。

| 指标（历史观测，已作废） | 实测 | 对照预算 | 结论 |
| --- | --- | --- | --- |
| 二进制体积 | 6,209,698 字节 | 25 MiB（26,214,400 字节） | 占 23.7%，健康 |
| 默认参数空载 VmRSS | 8,472 KiB | 8,192 KiB | 超 280 KiB，M1–M3 记 WARN |
| 调参后 VmRSS 中位数 | 7,832 KiB | 8,192 KiB | 余量 360 KiB（4.4%），趋势项 |
| 调参后拆分 | RssAnon 2,696 / RssFile 5,136 | — | 合计 7,832，对得上 |
| 调参后 Threads / fd / 空闲 CPU / 出站 / 定时器 | 13 / 6 / 0ms per 60s / 0 / 0 | 见 G-19 | 全部达标 |

上述历史值（8,472 / 7,832 / 2,696 / 5,136）均在"GC 被关闭"或"线程数非预期"状态下采集，**已作废**，不作为基线；保留它们只为记录排查过程。

**修复后观测值（M1 观测，非收口判据）**：修复 GC 被关闭的缺陷后（commit `02d0154`，G-21 门禁落地），默认档实测 VmRSS 中位数 **7,688 KiB**（min 7,608 / max 7,688 / p95 7,688）、Threads 12、空闲 CPU 0ms/60s、fd 6；300 次 healthz 触发 **1,374 次 GC**（缺陷版全程 1 次）。**该值作为 M1 观测值，不作为收口判据**——收口在 M4 集中瘦身后按 8 MiB 红线判。

默认参数是 `GOGC=100`、无 GOMAXPROCS 限制、`GOMEMLIMIT=6MiB`。也就是说：**按文档原样跑，预算是超的**。8 MiB 是产品承诺，超 280 KiB 就是承诺没兑现，不是"下次再看"的偏差。

## 决策

**本 ADR 的层级定位（重要）**：这里记录的是**代码层调参**（`GOGC=50` / `GOMAXPROCS=8` / `GOMEMLIMIT=6MiB`）。按 VISION「设计优化优先于代码优化」原则，它不是薄壳达标的主要功臣——主要功臣是设计层选择（薄壳内核不内置业务、第三方依赖 ≤3、前端 embed 单二进制、无 Web 框架）。**调参是最后一步，且有天花板**：`GOGC` 再降只会增加 GC 频率而不减 RssFile（代码页），`GOMAXPROCS` 再降会牺牲并发。

因此本 ADR 的两个旋钮标注为**临时手段**，复审条件里追加：若 M4 集中瘦身后设计层腾出足够空间，**应优先回退到 `GOGC=100`** 以降低 GC 频率，除非实测证明 50 档明显更优。

1. 运行时默认改为 **`GOGC=50`、`GOMEMLIMIT=6MiB`、`GOMAXPROCS=8`**（主壳是薄壳调度器，24 并发用不上）。
2. 内存证据口径保留多档：`GOGC=50`（**默认档**）/ `100` / 对照 `200`，各 60 点中位数 × 来源标注（`smaps_rollup` 或 `status`，须写明来源）。对外报告必须标档位，禁止拿 100 档数字报达标。
3. **余量按趋势监控，M4 统一收敛**：7,688/8,192 = **93.9%**（M1 修复后观测值），余量 504 KiB（6.2%）——登记为**趋势项**而非阻断项。M1–M3 期间在 ≤16 MiB 不阻断区内只记 WARN + 记趋势，不返工；M4 收口前集中瘦身（`go pprof` heap 定位常驻分配 → 砍依赖 / 延迟初始化 / 缩小缓冲区），收敛后再按 8 MiB 红线判 gate。**任何阶段都不抬预算。**

## 备选方案对比

| 方案 | 优点 | 代价 | 为何不选 |
| --- | --- | --- | --- |
| 抬预算到 16 MiB | 最省事，立刻"达标" | 违背 8 MiB 产品承诺；真实占用没降，只改了尺子 | 直接否：改标准不是解决问题 |
| 只降 GOGC，不设 GOMAXPROCS | 少一个变量，实测 8,040 KiB | 余量仅 152 KiB（1.9%），任何一次依赖升级都会破线 | 太险，等于把风险留给下一次提交 |
| **GOGC=50 + GOMAXPROCS=8**（选） | 7,832 KiB，余量 4.4%；并发上限与薄壳定位匹配 | GOGC 更低 → GC 更频繁；GOMAXPROCS=8 在多核机浪费并行度 | 选它：预算内且留出可观测余量 |
| `GOGC=off` + 纯 GOMEMLIMIT | 无 GC CPU 开销 | 内存到顶才回收，GC 抖动与延迟尖刺不可控 | HTTP/SSE 服务面不能接受不可预测延迟 |

## 后果

**正面**：空载 VmRSS 7,688 KiB（M1 修复后观测值）回到 8 MiB 预算内，余量 504 KiB 可被持续观测；GOMAXPROCS=8 把并发上限钉在薄壳定位上，长连接与插件调度不会无界抢核；三个参数都在 `main` 里显式设置且可被环境变量覆盖，消融实验成本低。

**负面**：`GOGC=50` 让 GC 频率翻倍，薄壳下 CPU 影响小，但 SSE 长连接多时需复测延迟；`GOMAXPROCS=8` 在 16 核以上机器主动放弃并行度，若未来某模块变 CPU 密集需重新评估。

**技术债**：`GOGC` 与 `GOMAXPROCS` 必须在 `cmd/kored/main.go` 显式设置且可从外部覆盖——否则实测数字无法复现；余量只剩 4.4%，M1-19 的 heap profile 不是可选项；"默认档 50 / 对照档 100" 的双档口径要固化进 G6 证据模板，避免档位混报。

## 预算分层（2026-11-22 修订）

产品红线（v1.0 / M4 收口）仍是主壳 ≤ 8 MiB；但 **M1–M3 期间只在不阻断区（≤ 16 MiB）之外阻断**——区间内未达红线只记 WARN + 记趋势，不返工。M4 前做一次集中瘦身（pprof + 依赖裁剪 + 延迟初始化）后再按红线判 gate。

采样精度同步分层：日常 `make mem` 5 点（约 10s），里程碑收口 `MEM_POINTS=60`（约 65s）；两者差异 < 10% 视为噪声，不重测。

**事故教训（不可再犯）**：曾因在日志里调用 `debug.SetGCPercent(-1)` 导致 GC 实际被关闭，GOGC 三档消融全部失效（详见 `.agents/JOURNAL.md` 事故记录与 G-21）。**任何"读取运行时配置"的实现都不得改变状态。**

**判别器必须能区分两种状态**：验证 GC 是否启用，唯一可靠的指标是 `/gc/gogc:percent`（off 时为大数），**不能**用"分配内存看 `NumGC` 是否增长"——在 `GOMEMLIMIT` 生效时即使 GOGC=off 也会因内存上限触发 GC（实测 churn 128 MiB 时 `numgc_delta=15`）。

## 验证方式

```bash
# 采样精度分层：日常 5 点（约 10s）；里程碑收口 MEM_POINTS=60（约 65s）
make mem                     # 默认 5 点，日常看趋势
MEM_POINTS=60 make mem       # 收口口径：60 点中位数（覆盖至少一个 GC 周期）
make budget-check            # 聚合门禁（RSS / 进程数 / 二进制体积）
make idle                    # 五项：CPU 时间、threads、fd、出站、定时器
# 必须记录生效值：启动日志里的 gogc_percent / gomaxprocs / gomemlimit
grep -E "gogc_percent|gomaxprocs|gomemlimit" /var/log/kore/kore.log | tail -3
# 三处设置可见；且不得出现"设置即读取"的副作用调用（G-21）
grep -n "SetMemoryLimit\|SetGCPercent\|GOMAXPROCS" cmd/kored/*.go
grep -rn "SetGCPercent(-1)\|SetMemoryLimit(-1)" --include='*.go' . || echo "无副作用调用"
```

## 复审条件

M2 引入更多模块后 VmRSS > 8,000 KiB（余量 < 2.3%）→ 重开，先 profile 再决定砍什么；`GOGC=50` 导致 API p95 > 50ms → 重开，评估分档 GOGC（空闲 50 / 高峰 100）或调整 GOMEMLIMIT；上游 Go 版本改变 GC 行为（如 GOGC 语义调整）→ 重跑基准后再定默认值。

**M4 瘦身冲刺完成后重评估**：若空载 VmRSS 在设计层优化后已 < 5 MiB 且有充足余量，**回退 `GOGC=100`**；若仍需 50 档才能守住 8 MiB，说明**设计层空间不足，重开设计评审**（而不是继续压 `GOGC`）。
