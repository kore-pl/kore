# ADR-0020: ACME 证书——不内置客户端，探测本机 certbot/acme.sh 且必须用户显式触发

## 背景

`ssl` 插件到 L1.5 后仍缺"公共 CA 证书"这条链路（PLUGIN-MATURITY §3.5 #5）：`ssl.issue`
返回 `E_UNSUPPORTED`，用户只能自签或手工导入。要补齐它，必须先回答一个绕不开的问题：
**ACME 协议客户端放在哪一层？** 三条硬约束同时压着这个决定：

1. **G-10 无联网**：内核与插件都不得后台联网、不得有隐藏上报；出站只能是用户显式动作。
2. **G-17 依赖白名单**：插件只依赖标准库 + `pluginapi`，不得引入第三方 ACME 库
   （`golang.org/x/crypto/acme`、lego 等都要破白名单）。
3. **G-19 / ADR-0019**：周期动作只能由内核 `scheduler` 发起；插件不得自起 ticker 续期。

同时 ACME 本身对运行环境有硬要求：域名解析可达、80/443 端口可被 CA 回连、需要账号注册
与证书链落盘。把它塞进"薄壳"代价很高，把它甩给用户又等于没补缺口。

## 备选方案对比

| 方案 | 依赖 / 体积 | 联网面 | 调度与续期 | 可验证性 | G-10 合规 |
| --- | --- | --- | --- | --- | --- |
| A. 内置 ACME 客户端（Go 实现或引库） | 破 G-17；自实现≥3k 行，二进制增大 | 插件进程直接出站 | 需自建续期时钟（破 G-19） | 需真 CA 账号才能验证 | 差——出站藏在插件里，审计面最大 |
| B. 调 `certbot` | 零 Go 依赖，依赖用户装包 | 外部进程出站 | 复用内核 scheduler 调 `ssl.renew` 检查 | 高——可断言 argv 与产物路径 | 好——命令、时机、参数全部可见 |
| C. 调 `acme.sh` | 零 Go 依赖，单 shell 脚本 | 外部进程出站 | 同上 | 高（与 B 同构） | 好 |
| D. 不做（维持自签 + 导入） | 零 | 零 | 无 | 无（无功能可验） | 完全合规但缺口未补 |

**A. 内置客户端**：能力最完整、体验最顺，但代价是三条硬约束全部破线——引库破 G-17，
插件进程出站让"无联网"从架构约束退化成口头承诺（G-10 审计只能靠翻代码），
而自动续期还得再要一个周期源（破 G-19）。对"薄壳 + 零常驻"的定位是设计层倒退。
**否决。**

**B. 调 certbot / C. 调 acme.sh**：插件不新增任何依赖，只做三件事——**探测**、
**在用户显式确认后以 argv 数组调用**、**把签出的证书导入自己的管理目录**。联网主体是
用户自己安装、自己运维的第三方二进制，kore 侧没有网络代码；命令与参数在调用点可见、
可审计、可测试（用真脚本替身跑通 argv 与产物）。续期仍然只由内核 scheduler 到点调
`ssl.renew`，插件不加时钟。**推荐 B 优先、C 兜底**（certbot 生态与续期约定更成熟；
acme.sh 在无 root / 精简发行版上更常见，检测顺序固定为 certbot → acme.sh）。

**D. 不做**：完全合规，但 ssl 的公共 CA 能力永久停在"手工导入"，与"生产级"定位冲突；
仅在"本机没有任何客户端"时作为**运行时降级**保留（`available=false` + hint 引导自签/导入），
不作为方案选择。

## 决策

采用 **B + C：探测本机外部客户端，用户显式确认后调用，签出证书导入管理目录**。
四道闸门保证"不越界"：

1. **默认零出站**：`ssl.acme.status` 只跑 `<tool> --version`（本地进程，不联网）；
   插件 Go 代码本身不发起任何网络请求。
2. **必须显式确认**：`ssl.acme.issue` 缺 `confirm=true` 直接 `E_INVALID` + hint，
   不落任何文件、不执行任何外部命令。
3. **不做后台自动签发/自动续期**：`ssl.acme.issue` 只能被用户显式调用；scheduler 任务
   调的是 `ssl.renew`，而 ACME 托管证书（issuer 命中 Let's Encrypt/ACME，或存在
   `<base>.acme` 标记）在 `ssl.renew` 里一律 `E_UNSUPPORTED` —— **绝不**后台跑 ACME。
4. **工作目录与私钥边界**：外部客户端状态全部落在 `<证书目录>/acme/<tool>`（0700），
   不写 `/etc/letsencrypt`、不写家目录；签出的证书经 `ssl.import` 的既有三重校验后入库，
   私钥只在磁盘上、只返回路径，返回值不含任何私钥内容。

## 上线顺序与运行环境

| 环节 | 归属 | 说明 |
| --- | --- | --- |
| 客户端安装 | 用户 / 发行版 | 插件不代装、不捆绑二进制（裁决 37 同理） |
| 域名解析 + 80 端口 | 用户 | `--standalone` 需要 80 端口可达；失败由工具输出尾部回报 |
| 账号与证书 | 外部客户端 | 账号密钥留在 `acme/<tool>`，由用户自行备份 |
| 续期触发 | 内核 scheduler（ADR-0019） | 到点调 `ssl.renew`；ACME 证书在此如实拒绝 |
| 卸载清理 | 用户 | 删除证书目录即清理；插件不写系统其它位置 |

## 后果

**正面**：三条硬约束零破线；插件零新依赖、二进制体积不变；能力对用户可见、可审计、
可用真脚本替身完整测试（探测 → 调用 → 导入 → 归属标记 → 续期拒绝）；无客户端时
降级路径清晰（自签/导入），不假装成功。

**负面**：用户必须先自己装 certbot 或 acme.sh；插件无法控制外部二进制的版本与行为差异
（参数拼装按两家的公开 CLI 约定，版本差异靠 `--version` 探测暴露给用户）。

**技术债**：
① 只实现"首次签发 + 导入"，ACME 证书的**自动续期**仍是外部工具职责（用户在
   工具侧配 cron 或手工重跑 `ssl.acme.issue`）——本 ADR 明确不在内核侧后台跑 ACME；
② `--standalone` 需要 80 端口空闲，与站点插件共存时会冲突，需用户改用 webroot
   （当前未暴露 webroot 参数，v1.1 评估）；
③ 仅支持 standalone；DNS-01 / wildcard 未支持。

## 验证方式

```bash
cd kore-plugin-ssl
gofmt -l . && GOWORK=off go vet ./... && GOWORK=off go test -timeout 200s ./...
# 探测与调用：真脚本替身断言 argv、导入结果、.acme 标记、续期拒绝（internal/certs/acme_test.go）
# 真机：本机无 certbot/acme.sh → ssl.acme.status {available:false}；
#       confirm 缺失 → E_INVALID；confirm=true 且无客户端 → E_UNSUPPORTED + hint
curl -s -b cookies -H "X-Kore-CSRF: $CSRF" -H 'Content-Type: application/json' \
  -X POST http://127.0.0.1:18860/api/v1/invoke/ssl/ssl.acme.status -d '{}'
```

## 复审条件

- 本机装了 certbot/acme.sh 后，需补一次真实签发验收（当前机器无客户端，只有替身证据）。
- 若站点插件与 `--standalone` 的 80 端口冲突成为常态，重新评估 webroot 参数与优先级。
- 若 G-10 放开"可配置的出站白名单"，重新评估是否需要内核侧 ACME 任务封装。
- 若外部客户端 CLI 出现破坏性变更（参数名/输出路径），按新版本调整 `acmeArgs` 与
  `issuedPathCandidates`，并同步本 ADR 的"技术债"。
