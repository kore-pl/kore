# ADR-0013: 极致资源压缩——插件三态 + 常驻配额 ≤3

## 背景

用户原话：「性能和资源消耗需要极致的压缩，它是管理者，不能变成服务器的负担。」而 v1 要对标专业版 = 18–22 个插件。若按"一插件一常驻进程"实现，面板自身会吃掉数百 MiB 内存与数十个进程，从"运维工具"退化成"运维负担"，直接违背形态锚点（无存在感常驻者）与资源锚点。

真正的问题不是"每个插件省几 MiB"，而是**同时活着的进程数**。22 × 12 MiB = 264 MiB 是结构性的，不是优化能填的坑；必须让"绝大多数插件在绝大多数时间不存在"。

## 决策

1. **插件生命周期三态**：`resident`（必须实时响应）、`lazy`（**默认**，空闲 300s 退出，冷启动 p95 ≤ 300ms）、`oneshot`（执行完退出）。
2. **同时常驻插件 ≤ 3**（硬门禁）；常驻合计 ≤ 24 MiB、单个 ≤ 12 MiB。配额满时新 `resident` 申请被拒或触发抢占，不允许静默超配。
3. **主壳空闲**：CPU ≤ 0.1%、goroutine ≤ 20、打开 fd ≤ 64、**零轮询**（状态变化走事件推送 + SIGHUP，人间隔内不做定时拉取）、空载出站 0。
4. **冷启动约束分两层，不能合成一个数**：插件 init 不做网络请求、不连 DB、不扫大目录。**硬超时 2s**（与 [PLUGIN-PROTOCOL](../PLUGIN-PROTOCOL.md) 一致）：exec 到 `kore.hello` 完成超过 2s → 判启动失败、SIGKILL、计重启次数；**性能 SLO 300ms**：从"发起业务调用"到"插件 ready"的目标值，超 300ms **不算失败**，只算性能不达标，由 `make budget-check` 与 M1 性能验收判定。两层合并会混淆"正确性"与"性能"——2s 管能不能活，300ms 管好不好用。
5. **22 个插件中常驻者应 ≤ 3**：site 网关类 + 必要的健康探测；其余默认 `lazy` 或 `oneshot`。`lazy` 必须在 300s 空闲后真正退出，不得内部起 ticker 续命。

## 备选方案对比

| 方案 | 优点 | 代价 | 为何不选 |
| --- | --- | --- | --- |
| 全部常驻 | 实现最简单，无冷启动问题 | 22 进程 × 12 MiB ≈ 264 MiB，直接违背"不成负担" | 结构性超预算，优化无法弥补 |
| 全部 oneshot | 内存最省，空闲严格为 0 | 每次请求冷启动，站点管理类交互体验不可接受 | 与"效率优先"体验锚点冲突 |
| 全部 lazy | 省内存且保留常驻语义 | 冷启动延迟与状态丢失要逐个插件处理；高频插件反复启停 | 高频路径被冷启动拖垮 |
| resident / lazy / oneshot 三态 + 配额 ≤3（选） | 空闲约 1 进程 + 0~3 插件；高频留常驻、低频零驻留 | 需要调度策略与冷启动测量 | 选它：把"进程数"变成受配额约束的资源 |

## 后果

**正面**：空载 ≈ 1 个进程 + 0–3 个插件，符合"无存在感"；常驻合计 ≤ 24 MiB 让主壳 + 插件在 1C/512M 机器上仍有富余；零轮询让空闲 CPU 真正接近 0，而不是"低但持续"。

**负面**：`lazy` 冷启动给首次请求增加延迟（目标 p95 ≤ 300ms，低配机可能超标）；插件必须无状态或能快速恢复状态，否则退出即丢上下文；常驻配额需要抢占/排队策略，否则"谁先申请谁常驻"。

**技术债**：`lazy` 状态恢复路径要逐插件测试；常驻配额抢占策略要定（按调用频次还是声明优先级）；冷启动 p95 需持续测量（发布前 + 低配机），不能只测开发机；`oneshot` 每次启动的进程创建成本要在容量规划里算进去。

## 验证方式

```bash
# 空载进程数：1 主壳 + 0~3 常驻
pgrep -c kored && pgrep -c 'kore-'          # 期望 1 与 ≤3
# 空闲 CPU：60s 内 utime+stime 增量 ≤ 60ms
awk '{print $14+$15}' /proc/$(pgrep -f 'kored$')/stat   # 间隔 60s 两次取差
# goroutine 与 fd 上限
ls /proc/$(pgrep -f 'kored$')/task | wc -l   # ≤ 20
ls /proc/$(pgrep -f 'kored$')/fd | wc -l     # ≤ 64
# 空载零出站
ss -tnp | grep kored || echo "空载零出站"
# lazy 插件 300s 后进程消失，下一次调用 p95 ≤ 300ms
sleep 310 && pgrep -f 'kore-<lazy-id>' || echo "已退出"
```

## 复审条件

紧凑型服务器（1C/512M）上仍被投诉占资源 → 进一步下调为"主壳 + 0 常驻"，把 site 也改成 lazy 并接受冷启动；`lazy` 冷启动在低配机器上 > 1s → 对高频插件升为 `resident` 并重新分配配额（上限可提到 4，需新 ADR）；若配额长期被打满且频繁抢占 → 说明三态划分与实际调用分布不符，需重定插件分类。
