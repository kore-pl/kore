一句话定位：**kore 是极简内核驱动、插件定义能力、资源零侵占、完全归属使用者的服务器运维基础底座。**
它不是"大而全面板"，是**薄壳调度内核**——内核只定规则（插件生命周期 / 权限校验 / 消息路由 / 资源隔离），不内置任何运维功能。

## 1. 问题陈述：传统面板为什么越做越重

传统运维面板的膨胀是一条**单向因果链**，每一环都有可观测现象，不是主观感受：

```
功能全塞进一个进程
  └→ 依赖图膨胀          空载 RSS 180–600 MiB，冷启动 3–20 s
       └→ 升级必须整体重启  影响面 = 100% 功能，窗口 5–30 s
            └→ 扩展只能 fork  定制与上游冲突，升级即丢失本地改动
                 └→ 数据与账号托管在面板  迁移需导出专有格式，离线不可自证

另一条并行支路：
默认开一堆常驻定时器与采集器
  └→ 空转占用不可回收    空载 CPU 1–5%，内存随时间抬升
       └→ 用户为了"用得上"接受全部功能  锁定期望被默认接受
```

| # | 因果环节 | 机制 | 可观测现象 | 度量方式 |
| --- | --- | --- | --- | --- |
| 1 | 功能内聚导致进程与依赖膨胀 | 每个新功能都要进主进程，依赖只能加不能减 | 面板进程 RSS 180–600 MiB；依赖 40+ Go module / 200+ npm 包 | `ps -o rss= -p PID`；`go list -m all \| wc -l` |
| 2 | 单体升级影响全域 | 二进制单进程，改一行也要整体重启 | 升级窗口 5–30 s，期间所有功能不可用 | 升级时 `while :; do curl -s -o /dev/null -w '%{http_code}\n' ...; sleep 1; done` 断流计数 |
| 3 | 数据/账号托管造成锁定期望 | 账号体系、授权校验、遥测、专有导出格式捆绑 | 断网后面板功能受限；迁移只能导出专有备份包 | 断网 + 新建账号 + 调一个只读功能，看是否可用 |
| 4 | 常驻定时器默认开启 | 采集、巡检、清理等定时任务默认常开 | 空载 CPU 持续 1–5%，内存缓慢抬升；进程数随功能增加 | `pidstat -p PID 60 1`；`ls /proc/PID/task \| wc -l` |
| 5 | 扩展必须改源码 | 没有插件协议，第三方只能 fork 或提 PR 进主干 | 定制分支与上游冲突；升级即丢定制 | `git log --merges` 与定制补丁数、每次升级的冲突文件数 |

**结论**：膨胀不是"功能多"，是**内核与业务没有边界**。只要业务能进内核，内核就必然长大；只要内核长大，升级影响面和资源占用就必然失控。kore 的答案是把边界做成**物理边界**（进程 + UDS + 协议），而不是代码规范。

## 2. 顶层抽象目标

**把"运维能力"从内核里赶出去，内核只保留四件规则性工作：插件生命周期、权限校验、消息路由、资源隔离；所有运维功能以独立进程插件形式存在，可装、可卸、可替换，内核代码不因新增功能而变化。**

三句展开：

1. **规则与业务分离**：内核是"调度器 + 校验器 + 路由器"，插件是"能力的全部实现"。新增一个运维能力，主壳二进制不变、主壳代码零改动。
2. **资源可归零**：常驻是有代价的特权，只有必须常驻的能力（如站点管理）才常驻；低频能力按需唤起、用完即退，空闲 RSS 严格为 0（进程不存在）。
3. **归属使用者**：无强制账号、无联网校验、无隐藏上报、无审核；代码开源、配置明文、协议开放，用户随时可以 fork、改配置、拔插件、迁移数据。

## 3. 五锚点

每个锚点给"含义 / 反例 / 可验证判据"。判据必须是量化或可观测项，不接受"感觉轻了"。

### 3.1 形态：无存在感常驻者

- **含义**：平时几乎不可见（内存个位数 MB、无后台任务噪音），需要时被唤起，用完即退；用户只在"要操作"时感知到它。
- **反例**：开机自启一堆采集器、面板首页堆 6 个实时图表轮询、每次打开先拉 3 个统计接口。
- **可验证判据**：
  - 主壳空载 RSS **硬红线 ≤ 16 MiB、目标 8 MiB**（对外承诺以硬红线为准；运行时默认 `GOGC=50` + `GOMEMLIMIT=6MiB` + `GOMAXPROCS` 上限 8（仅 CPU>8 时收敛），锚点在 `cmd/kored/serve.go` 的 `setRuntimeLimits()`，见 ADR-0015）：`ps -o rss= -p $(pgrep -x kored) | awk '{printf "%.2f\n",$1/1024}'`
  - 无触发时一次性插件进程数 = 0：`pgrep -fc 'kore-(backup)'` 输出 `0`
  - 默认零后台定时器：`grep -rn "time.NewTicker\|time.NewTimer" internal/` 仅命中证书续期检查包，且该功能默认关闭（唯一允许的常驻定时器，开关由 `DATA-MODEL.md` §3 登记）

### 3.2 架构：内核只定规则不做业务

- **含义**：`internal/core/` 只允许出现协议、路由、状态机、存储、鉴权、日志；不允许出现任何"站点 / 备份 / 证书 / 数据库"业务语义。
- **反例**：内核里预置"一键备份"、"站点模板"、"计划任务"这类功能；内核 import 任何插件仓库的代码（插件在独立仓库，不在 kore 子目录）.
- **可验证判据**：
  - `go list -deps ./cmd/kored | grep -c '^kore/plugins'` 输出 `0`
  - `grep -rniE "wordpress|nginx|mysql|backup|site\b" internal/core/ --include=*.go` 输出为空（白名单词表见 [CORE.md](./CORE.md) §9）
  - 新增一个插件后主壳源码 diff 为 0 行（`git diff --stat cmd/ internal/` 为空）

### 3.3 资源：内核个位数 MB，低频功能零常驻

- **含义**：资源预算写进门禁，不是"尽量省"。主壳空载 **目标 ≤ 8 MiB、硬红线 ≤ 16 MiB**；**同时常驻插件 ≤ 3 个（推荐 ≤ 2）**，单个 **目标 ≤ 12 MiB / 红线 ≤ 24 MiB**，合计 **目标 ≤ 24 MiB / 红线 ≤ 48 MiB**；lazy 空闲 300 s 退出、一次性插件空闲 RSS = 0。定案依据 ADR-0016：除安全事故或用户明确要求外不再调整。
- **反例**：常驻插件随手 150 MiB；"为了快"把一次性功能也常驻；用内存换开发速度。
- **可验证判据**：
  - 主壳：60 s 稳定后取 3 次中位数 **≤ 16 MiB 为达标红线、≤ 8 MiB 为目标**（口径 `ps -o rss= -p PID`，KiB/1024）
  - 常驻插件：进程数 ≤ 3，`sum(rss) ≤ 24576 KiB` 且单插件 `≤ 12288 KiB`
  - 一次性插件：空闲时 `pgrep -fc kore-backup` 为 0；触发执行峰值 ≤ 16 MiB，退出后 500 ms 内进程消失
  - 单二进制 ≤ 25 MiB（含 embed 前端）：`du -b bin/kored`

### 3.4 开放：代码开源、配置明文、协议开放

- **含义**：无账号（本地单用户）、无联网校验、无隐藏上报、无审核；协议文档化，第三方按协议即可接入；配置是明文字段，手改 + SIGHUP 生效。
- **反例**：装插件要登录云端账号；启动时 ping 授权服务器；"高级功能"被 license 锁；配置加密或只存数据库。
- **可验证判据**：
  - 断网可用：`ss -tnp | grep kored` 在空载时输出为空（除用户主动请求）
  - 无上报：`grep -rniE "telemetry|analytics|report_event|license_key" internal/ cmd/` 输出为空
  - 配置明文：`test -r /etc/kore/config.yaml && grep -c ':' /etc/kore/config.yaml` > 0
  - 协议可自实现：一个独立仓库的新插件只依赖 `pkg/pluginapi` 的帧格式、4 个必选方法（hello/ping/shutdown/reload）与 1 条必选事件通道（`kore.event`）即可握手成功（M1 用 `kore-plugin-echo` 验证）

### 3.5 体验：效率优先

- **含义**：合理信息密度、最短路径、克制视觉；拒绝大卡片、过度动效、工业样板；默认暗色、高信息密度。
- **反例**：首页 4 个大卡片占满首屏；每个操作 3 次确认弹窗；加载动画 800 ms 起。
- **可验证判据**：
  - 前端首屏 ≤ 300 KiB gzip：**首屏 = `index.html` + 其直接引用的 JS/CSS**，逐文件 `gzip -c` 后求和；插件资产、图片、字体不计入。命令：`for f in web/dist/index.html $(grep -oE '/assets/[^"]+\.(js|css)' web/dist/index.html | sed 's#^/#web/dist/#' | sort -u); do gzip -c "$f"; done | wc -c`
  - 核心路径步数：登录 → 查看插件状态 ≤ 2 次点击；登录 → 调用插件方法 ≤ 3 步
  - 无阻塞动效：交互反馈 ≤ 100 ms 出现（骨架/禁用态），无超过 300 ms 的全屏过渡
  - 默认暗色 + 表格密度：表格行高 ≤ 32 px，首屏可见列 ≥ 6

## 4. 与传统面板对照表

| 维度 | 传统面板 | kore | 差异根因 |
| --- | --- | --- | --- |
| 架构 | 单体进程 + 功能模块内聚 | 薄壳内核 + 独立进程插件 | 边界是进程，不是代码规范 |
| 资源 | 空载 180–600 MiB，常驻一堆定时器 | 内核 目标 8 MiB / 红线 16 MiB；同时常驻 ≤3 个（推荐 ≤2）/ 单目标 12、红线 24 MiB；其余 lazy/oneshot 空闲 0 | 资源预算进门禁，超了不合并 |
| 扩展方式 | 改源码 / fork / 官方插件市场 | 装 `<id>-<version>.tar.gz`，协议 `kore.plugin.v1` 即可接入 | 协议先于功能，第三方不需要读内核代码 |
| 升级影响面 | 100% 功能同时中断 5–30 s | 内核升级只影响主壳与在途请求；插件可单独热升级（新进程 hello 成功再停旧进程） | 进程隔离把影响面切成块 |
| 开放性 | 账号 + 联网校验 + 专有备份格式 | 无账号、无联网校验、无上报；配置明文、数据在 `/var/lib/kore` 可直读 | 归属使用者，不做锁定期望 |
| 可审计性 | 行为藏在编译产物与闭源服务里 | 单二进制 + 明文配置 + 明确日志路径 `/var/log/kore/`；协议帧可抓 | 一切可观测项都落在文件系统上 |
| 失败域 | 一个模块 panic 拖垮全部功能 | 插件崩只影响该插件；内核崩由 systemd 拉起，插件状态从 bbolt 恢复 | 故障域与进程边界一致 |
| 拥有权 | 厂商拥有升级节奏与数据格式 | 用户拥有二进制、配置、数据、插件源码；可整体迁走 | 无云端依赖，退出成本接近 0 |
| 学习成本 | 功能多但语义封闭，排障靠厂商文档 | 只有 4 个必选方法 + 1 条事件通道 + 8 个错误码，排障靠 `kore.log` 与帧日志 | 内核小 = 心智模型小 |

## 5. 谁该用 / 谁不该用

### 5.1 该用

1. **只有 1–5 台自管服务器、想要"能看见、能改、能迁走"的运维入口**的个人或小团队：单二进制 + 明文配置，出问题能自己读代码。
2. **把服务器当资产而不是平台**、明确拒绝把账号和数据托管给第三方面板的人：无账号、无联网校验，断网全功能可用。
3. **需要按需扩展能力、但不想 fork 面板**的团队：写一个插件按协议接入，主壳零改动，升级不丢定制。
4. **资源敏感环境**（1 GB 内存 VPS、边缘小机器）：内核目标 8 MiB（硬红线 16 MiB），低频功能零常驻，不会为了面板多买一台机器。

### 5.2 不该用（敢写）

1. **需要多租户、按用户隔离资源的 SaaS 场景**：kore 是单用户单实例模型（`/etc/kore/config.yaml` + 一个 `kore_session`），多租户要重做鉴权与数据分区，属于非目标。
2. **需要集群、跨机编排、分布式调度**：kore 明确不做集群与分布式，多机请每台各装一个，不提供聚合视图。
3. **需要"拖拽建站 / 可视化编排"的重型面板用户**：kore 不做拖拽建站，站点只是 `site` 插件的一个能力，UI 是表格与表单，不是画布。
4. **要求开箱即用、不接受动手配置的人**：kore 的定位是"薄壳 + 你决定装什么"，默认只保证内核可跑与健康检查；想要 60 个功能一键开启，请用传统面板。

## 7. 设计原则

此前的原则散在 §2 的三句展开与各锚点反例里；从本节起统一收口，后续新增原则按序编号（**当前最后一条 = 原则 1**）。

**原则 1：设计优化优先于代码优化。**

遇到资源 / 性能 / 复杂度问题时，先问"能否改设计"，再问"能否调参数"。调参是在既有形状里挤空间，有天花板；设计是换一个占用更小的形状，没有天花板。

判定顺序（三步，不得跳）：

1. **设计层**：能不能少一个进程 / 少一个依赖 / 少一层转发 / 少一份拷贝 / 改生命周期（`resident`→`lazy`→`oneshot`）/ 改触发方式（自建 scheduler→宿主 timer）？
2. **架构层**：能不能改边界（谁能看到谁）、改时机（延迟初始化）、改存储（内存→磁盘）、改协议（少一次往返）？
3. **代码层**：只有前两步都穷尽后，才允许调参（`GOGC` / `GOMAXPROCS` / 缓冲大小 / 超时值），且必须记 ADR 并标注"临时手段，待设计层解决"。

**反例（本项目已发生）**：为把空载 RSS 压几百 KiB 而调 `GOGC` + `GOMAXPROCS`——这属于第 3 步，**不是**达标的主要功臣；主要功臣是"薄壳内核 + 依赖白名单 ≤3 + 前端 embed 单二进制"这些**设计选择**。参数只是把设计留出的余量用掉，设计才是余量本身。

| # | 非目标 | 为什么不做 | 强做的代价 |
| --- | --- | --- | --- |
| 1 | 容器编排（K8s/Swarm/Compose 管理） | 与"直接与宿主 systemd/cgroup/文件系统交互"的红线冲突；容器底座会引入运行时 SDK 依赖，主壳体积与权限模型失控 | 依赖白名单破防（容器运行时 SDK），内核从 MB 级涨到数十 MB |
| 2 | 多租户 SaaS | 单用户单实例是资源与鉴权模型的前提；多租户要重做会话、数据分区、配额 | 鉴权与存储复杂度翻倍，RSS 与代码量同步翻倍 |
| 3 | 集群 / 分布式 | 分布式一致性是另一个产品；kore 的失败域假设是"单机单进程树" | 需要共识协议与常驻中间件，直接踩红线② |
| 4 | 拖拽建站 | 可视化画布与"克制视觉、高信息密度"冲突；建站是 `site` 插件能力，不是内核职责 | 前端体积破 300 KiB 首屏预算，内核被迫理解站点语义 |
| 5 | i18n 全量框架（MVP 仅中文 + 英文可选骨架） | 全量双语会把每条文案变成 key + 资源文件，增加 20%+ 改动面却无人受益；「中文为主、英文为辅」的导航/通用/设置骨架已按 [ADR-0021](./DECISIONS/0021-i18n.md) 单独收敛 | 文案改动成本翻倍，前端包体增大，M2 排期被吃掉 |
| 6 | 移动 App | 响应式 Web 已覆盖应急操作场景；原生 App 要维护第二套鉴权与发布链路 | 多一套客户端与发布流程，收益仅为"手机上更好点" |
| 7 | 重型主题系统 | 主题引擎（变量、皮肤包、在线市场）与"体验效率优先"冲突；暗色 + 一套 token 足够 | 前端复杂度上升，主题包成为新的分发与审核面 |
